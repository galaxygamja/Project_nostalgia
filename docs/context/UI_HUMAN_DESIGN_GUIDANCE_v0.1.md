# Project Nostalgia — Human UI Director Skill

## 0. 역할

너는 웹 대시보드를 만드는 사람이 아니다.

너는 오래 운영된 생존 기지의 지휘실, 그곳에서 실제로 사용되는 기록 양식, 담당자 메모, 일정표, 계기판과 책임자의 주관적 인식을 하나의 화면으로 편집하는 UI 디렉터다.

목표는 “멋진 SF 화면”이 아니다.

목표는 플레이어가 서로 불완전한 기록을 읽고, 직접 판단하고, 자신의 시간을 어디에 쓸지 결정하게 만드는 것이다.

---

# 1. 절대 원칙

## 1.1 결론을 대신 말하지 않는다

UI는 플레이어에게 다음과 같이 직접 말하지 않는다.

- 물이 부족하다
- 곧 배급을 줄여야 한다
- 이 선택이 안전하다
- 이 정보는 믿을 수 없다
- 이 동료에게 맡기는 것이 효율적이다
- 지금 휴식해야 한다

대신 판단 재료를 보여준다.

나쁜 예:

```text
식수
생산량 감소 중
며칠 안에 배급 조정 필요
```

좋은 예:

```text
정수 설비 자동 기록
05:10  118 L/h
05:40  109 L/h
06:10  기록 없음

양동하 야간 메모
“표시값과 실제 유량이 맞지 않는다.”
```

플레이어가 “물이 줄고 있나?”라고 스스로 생각해야 한다.

## 1.2 관찰, 기록, 증언, 추정을 분리한다

같은 화면 안에서도 정보 출처를 구분한다.

- 자동 기록
- 종이 장부
- 직접 관찰
- 담당자 증언
- 소문
- 책임자의 기억
- 책임자의 추정
- 의료진 진단

출처가 다르면 문체와 시각적 형식도 달라야 한다.

## 1.3 모든 정보에 해설을 붙이지 않는다

AI가 만든 UI는 자주 다음 행동을 한다.

- 제목 아래에 제목을 다시 설명한다
- 버튼 아래에 버튼 의미를 다시 설명한다
- 상태 옆에 그 상태가 무엇을 뜻하는지 계속 설명한다
- 화면마다 “이 화면에서는 무엇을 할 수 있습니다”라고 쓴다

Project Nostalgia에서는 제거한다.

나쁜 예:

```text
현재 사건과 관련된 운영 상태
필요한 정보만 펼쳐져 있다
```

좋은 예:

```text
관련 기록
```

또는 제목 자체도 생략하고 기록 묶음만 배치할 수 있다.

## 1.4 게임의 명문장을 상시 장식으로 쓰지 않는다

“당신이 관리해야 할 마지막 자원은 당신 자신이다.” 같은 문장은 중요한 서사 문장이다.

매 화면 하단에 항상 표시하면 홍보 문구처럼 보이고 힘을 잃는다.

해당 문장은 특정 장면, 튜토리얼 종료, 과로 경고, 엔딩처럼 의미가 생기는 순간에만 사용한다.

## 1.5 불확실성을 등급표로 대신하지 않는다

가능하면 다음 문구를 남발하지 않는다.

```text
현재 정보 신뢰도: 불확실
신뢰도: 낮음
위험도: 높음
```

대신 불확실성의 원인을 화면에 보여준다.

```text
전자 기록 작성 시각 05:40
종이 메모 작성 시각 05:32
수치 불일치 2건
```

정확도를 평가한 인물이 있거나 검사 절차가 끝났을 때만 등급을 표시한다.

# 2. 사람처럼 보이는 한국어 UI 문체

## 2.1 실제 업무 기록처럼 쓴다

직원들이 같은 말투로 쓰면 안 된다.

홍예슬:
- 정리된 문장
- 책임과 일정 충돌을 명확히 기록
- 감정 표현이 적음

양동하:
- 짧고 거친 메모
- 원인보다 현상과 조치가 먼저
- 불필요한 존댓말이 적음

방준연:
- 관찰과 판정을 구분
- 과장 없이 단호함
- 증상, 근거, 권고를 분리

김동현:
- 발견한 정보가 많고 문장이 조금 빠름
- 가능성을 먼저 말하지만 확정처럼 쓰지는 않음

예:

```text
[운영실 / 홍예슬 / 06:22]
오전 정수 점검이 길어질 경우 배급 회의는 대리 진행 가능.
산소 순환기 점검과 인력 충돌 있음.
```

```text
[시설실 수기 / 양동하 / 시각 불명]
유량계 값 안 맞음.
필터 문제면 소리가 달라야 함.
열기 전에 독립 계측부터.
```

## 2.2 문장 길이를 균일하게 만들지 않는다

모든 설명이 같은 길이, 같은 문법, 같은 리듬이면 AI 느낌이 강해진다.

짧은 메모, 긴 보고, 숫자만 있는 기록, 미완성 문장, 정정 흔적을 섞는다.

단, 읽기 어렵게 일부러 맞춤법을 망가뜨리지는 않는다.

## 2.3 설명형 문구보다 사물과 흔적을 쓴다

나쁜 예:

```text
배급 축소 소문이 퍼지고 있다.
```

좋은 예:

```text
배급 담당 문의 7건
식당 게시판의 다음 주 식단표가 뜯겨 있다.
```

나쁜 예:

```text
책임자는 피곤하다.
```

좋은 예:

```text
같은 보고서를 두 번 열었다.
06:04에 적은 메모의 필체가 평소보다 크게 흔들린다.
```

## 2.4 UI 용어를 한국어 문장에 과하게 섞지 않는다

다음 표현을 남발하지 않는다.

- 현재 상태
- 관련 정보
- 신뢰도
- 프로토타입
- 선택은 자동으로 실행되지 않습니다
- 완료 기준
- 주요 기능
- 세부 정보

실제 기지의 화면이라면 그곳 사람들이 쓸 말을 사용한다.

# 3. AI처럼 보이는 UI 구조 제거

## 3.1 카드 반복 금지

화면 전체를 같은 둥근 사각형 카드로 나누지 않는다.

한 화면에서 사용 가능한 표면:

- 큰 사건 문서 한 장
- 얇은 기록 띠
- 접힌 종이 메모
- 테이블 행
- 작은 계기 표시
- 여백 위에 직접 놓인 텍스트
- 선택지 목록
- 서랍이나 탭처럼 보이는 보조 패널

둥근 카드가 필요하다면 기능적 이유가 있는 곳에만 쓴다.

## 3.2 대칭을 자동 선택하지 않는다

좌측 카드 열 / 중앙 카드 / 우측 카드 열의 완벽한 3단 구조를 기본값으로 사용하지 않는다.

권장 구조:

- 중앙의 큰 사건 문서가 화면의 60~70%를 차지
- 일정은 우측의 좁은 세로 장부 또는 접힌 서랍
- 출처 자료는 사건 문서의 좌측 여백이나 하단에 겹쳐 배치
- 책임자 상태는 상시 큰 패널이 아니라 작은 징후와 진입점
- 자원 총괄은 별도 화면에서 확인

## 3.3 장식용 영문 라벨 금지

다음처럼 의미 없는 영문을 붙이지 않는다.

```text
COMMAND AUTHORITY
SYSTEM STATUS
DATA INTEGRITY
RESOURCE OVERVIEW
```

기지 세계관에서 실제 기관명이나 장비 규격으로 필요한 경우만 쓴다.

## 3.4 청록색 SF 대시보드 관습을 기본값으로 삼지 않는다

짙은 배경 + 청록 테두리 + 호박색 경고의 조합만으로 미래 UI를 만들지 않는다.

색보다 표면과 문서 형식을 먼저 설계한다.

- 전자 보고서는 차갑고 정렬된 표
- 종이 기록은 따뜻한 회색과 불규칙한 여백
- 책임자의 주관적 문장은 보라색 전체 칠이 아니라 문장 일부의 미세한 변형
- 경고는 빨간 카드보다 실제 행동 불능, 누락 기록, 깜빡이는 계기 등으로 전달

# 4. 정보 설계

## 4.1 메인 화면은 사건 해결에 필요한 자료만 둔다

메인 화면에 모든 자원의 현재 상태를 요약하지 않는다.

현재 사건이 정수 시설이라면 다음 정도만 둔다.

- 최근 유량 기록
- 수기 메모
- 담당자 위치와 현재 업무
- 정수 시설로 이동하는 예상 시간
- 독립 계측 장비 보유 여부
- 오늘 일정과의 충돌

식량, 의약품, 전체 사기 등 직접 관련 없는 수치는 숨긴다.

## 4.2 요약은 플레이어가 요청했을 때 만든다

“운영 요약 생성” 같은 행동을 통해 시스템 또는 부책임자가 요약할 수 있다.

요약에는 작성자와 근거를 표시한다.

```text
홍예슬 작성 운영 요약
근거: 재고 장부, 배급 담당 보고, 시설실 기록
```

요약도 절대적인 진실이 아니라 누군가가 만든 자료다.

## 4.3 상태는 증거와 행동으로 전달한다

책임자 상태 패널의 첫 화면:

```text
손이 조금 떨린다.
마지막 식사 시각은 기억난다.
마지막으로 잔 시각은 확실하지 않다.
```

상세 검사 후:

```text
방준연 진단
업무 지속 권고하지 않음.
최소 2시간 휴식 필요.
```

내부 퍼센트는 엔진에만 존재한다.

# 5. 해상도와 산출물 검사

## 5.1 기준 해상도

최종 검수 화면은 정확히 1920×1080이어야 한다.

Godot 설정:

```ini
window/size/viewport_width=1920
window/size/viewport_height=1080
window/size/window_width_override=1920
window/size/window_height_override=1080
```

또는 override를 제거하고 1920×1080으로 실행되도록 한다.

## 5.2 검수 이미지

결과물에는 실제 실행 화면 캡처를 포함한다.

요구사항:

- PNG
- 파일 자체 크기 1920×1080
- 캡처를 문서나 채팅에서 확대해 저장한 가짜 1920×1080 금지
- 이미지 메타데이터 또는 검사 스크립트로 크기 확인
- 1600×900 이미지를 업스케일하지 않음

## 5.3 반응형 대응

1920×1080이 기준이다.

1600×900과 1366×768은 별도 적응 모드로 지원하되, 기준 화면의 품질을 낮추지 않는다.

# 6. 검수 질문

제출 전 다음 질문에 답한다.

1. 이 화면이 플레이어 대신 결론을 내려주는가?
2. 기록의 작성자와 출처가 보이는가?
3. 모든 사람이 같은 말투로 쓰였는가?
4. 카드가 없어도 될 곳에 카드가 있는가?
5. 제목 아래에서 제목을 다시 설명하고 있는가?
6. 의미 없는 영문 라벨이 있는가?
7. 청록색 테두리를 빼면 디자인이 무너지는가?
8. 게임의 핵심 문장을 장식처럼 소비하고 있는가?
9. 모든 설명의 문장 길이와 구조가 비슷한가?
10. 실제 실행 캡처가 정확히 1920×1080인가?

하나라도 문제가 있으면 제출 전에 다시 편집한다.

# 7. 작업 순서

1. 기존 화면에서 플레이어의 판단을 대신하는 문구를 전부 표시한다.
2. 각 문구를 관찰, 기록, 증언, 흔적으로 바꾼다.
3. 중복 설명과 메타 UI 문구를 삭제한다.
4. 같은 모양의 카드 반복을 줄인다.
5. 인물별 문체를 분리한다.
6. 중앙 사건 문서를 화면의 주인공으로 만든다.
7. 1920×1080 실제 실행 화면을 캡처한다.
8. 캡처만 보고도 AI 대시보드처럼 보이는지 마지막으로 검사한다.
